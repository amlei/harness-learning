# study-notes — 源码深挖成书

把一个开源仓库**读穿**，写成一本面向学习者的书式实现剖析，并产出可发布的多项目阅读站点。
**不是使用手册**，而是反过来追问"它是怎么被造出来的"。

## 输入

| 参数 | 说明 |
|------|------|
| 源码仓库路径 | 要剖析的上游仓库本地路径 |
| 上游官网 URL | **必填**——用于核验该仓库真实视觉风格（主题依据），勿臆测 |
| 作者 | 默认 `Amlei` |
| 输出仓库 | 本书站点仓库（默认即本 `harness-learning`） |
| 项目 slug | 如 `hermes`；内容落 `source/<slug>/` |

## 工作流

### 1. 勘察（recon）
读 `README` / `AGENTS.md` / 顶层 `pyproject.toml`·`package.json` / `docs/`，建立**子系统地图**与**文件依赖链**。
先想清楚"哪些是核心/关键机制（单独成一篇）、哪些可合并、哪些点到即止"——这是目录骨架。

### 2. 并行深挖（子代理）
对每个子系统派**子代理**，每个返回带 `文件:行号` 的密集技术简报（不是书稿）。
子代理 prompt 要点：读哪些文件、cover 哪些维度（设计目标 / 核心抽象 / 实现机制深挖 / 数据流 / 设计权衡 / 与其它子系统关系 / 边界情况）、引用真实代码、配 Mermaid/ASCII。
**并行**派发以省时；逐份读简报后再综合。

### 3. 综合成书（篇 / 章 / 节）
把简报综合成正文，覆盖 **设计思想 / 实现机制 / 实现原理** 三维度。
- **核心 / 关键功能实现机制单独成一篇**（如同步循环、工具注册表、会话库、技能 Curator、多终端后端、MCP、双消息守卫、委派/Cron/Kanban、安全边界、关键功能工具…各一篇）。
- 文件命名 `source/<slug>/part-NN-<kebab>.md`，`NN` 从 `00` 起（`00` = 概览）。
- 每篇首行 `# 第N篇　标题`，次行 `*作者：Amlei　·　更新时间：YYYY-MM-DD*`。
- 每篇末尾有"权衡总账"，收束设计取舍。

### 4. part-00 全文概览（**最后写**，但排第一篇）
包含：**序言**（受众、立场、反知识诅咒）+ **读者指南**（如何读、导航锚点）+ **概念入门**（释疑层，见下）+ **总目录**（每篇主旨 + 前置/延伸）+ **章节关系图**（Mermaid 依赖图）+ **贯穿主线**。

## 写作铁律

- **第三人称客观**。
- **受众是未知深度的学习者——切勿"知识诅咒"**。生僻术语（FTS5、WAL、CDP、SSRF、prefix cache、asyncio、ABC、MCP…）在 part-00「概念入门」用学习者级语言释疑；正文用到时以"概念见第0篇·X"回指。需要展开的背景知识就地加"知识补充"。
- **详略得当**：核心机制深挖到 `文件:行号`；边缘/产品化内容（计费、relay、特定平台怪癖）点到即止。
- **篇号用"第 N 篇"**（书的结构单位是"篇"，不是"部"）。
- **勘误**：与上游既有文档（如 CLAUDE.md）的出入要显式标注为更正。

## 交叉引用（关键）

正文凡提及其它篇的**具体章节**，把"第 N 篇·第 X 章 标题"写成 **markdown 链接**指向该篇文件名，可点击跳转：

```
[第三篇·第 6 章 工具集体系](part-03-tools.md)   →   （见[第二篇·第 5 章 缓存稳定性纪律](part-02-core-loop.md)）
```

- **必须具体到标题**（篇号 + 章号 + 章标题），不要只写 `[第三篇](part-03-tools.md)` 而不指明哪一章。读者点过去后要一眼知道找什么。
- 链接文本格式：`第N篇·第X章 标题`；如有节，加 `· X.Y 节标题`。
- **不转换**：当前篇自身篇号、标题行（`#`/`##`）、代码块与 Mermaid 图内、已是链接处。
- **不要用 `> 关联：…` 大段引用块**做关系说明——关系就地用链接表达。
- 全局关系另在 part-00「章节关系图」给一张 Mermaid 依赖图。

## 配图

配图的目的是**帮读者快速理解与加深印象**——用可视化的方式让复杂关系一目了然，减少认知负担。
- 复杂关系（架构 / 状态机 / 时序 / ER / 依赖图）用 **Mermaid**。
- 简单示意（数据流、依赖链、命令速查）用 **ASCII**。
- 每篇 1–3 张，配图必有简短图注说明它在讲什么。

## 阅读站点（配套产出，与前序一致）

复用本仓库**已存在**的阅读器套件，勿重造。结构详见 [`references/kit-and-themes.md`](references/kit-and-themes.md)：

```
<输出仓库>/
├── index.html              # 根目录页（仓库自身风格）—— 已存在，按需调主题
├── catalog.js              # 内容登记（项目/文章元数据）—— 加一行
├── reader/{reader.css,reader.js}   # 共享阅读器套件 —— 已存在，勿改
├── source/<slug>/
│   ├── index.html          # 本项目独立阅读器（自带主题 + 目录清单）—— 复制任一已有卷的改三处
│   └── part-*.md
└── paper/<slug>/           # 单篇文章（可选）
```

**新增一卷** = 复制任一已有卷的 `source/<slug>/index.html` → 新 `source/<新slug>/index.html`，改三处：`<html data-theme>`、品牌行/印记/favicon、内嵌 `window.READER`（home 元数据 + parts 清单）；在 `catalog.js` 加一行。**永不改 reader/ 套件或别的卷。**

### 主题 = 上游仓库的真实视觉风格（**勿臆测**）
- **先抓上游官网**真实配色：用无头浏览器（系统 Chrome + playwright-core）等 JS 框架充分水合后读 **computed style**（CSS 是 ground truth），再用视觉模型（GLM-5V-Turbo 等）识别截图交叉核验。
- **教训**：Hermes 官网曾被我误判为"白/近黑单色"，真实是**饱和品牌蓝 `#0000F2` + 白 + 极细衬线大标题 + 白线蓝图插画**（Next.js 未充分水合时读到的样式是错的）。务必实测。
- 主题在 `reader/reader.css` 的 `:root[data-theme="<slug>"]` 里定义一次（画布 + 文字 + 主色 + 字体 + `--ink-deep` + `--code-fg`），由 `<html data-theme>` 引用。根目录页用仓库自己的"house"主题。

### 阅读器是文档站式（为长时间阅读优化）
左锚定宽阅读列（正文 ~72ch，代码/表/Mermaid 突破到列宽）+ 右轨"本章目录"(scroll-spy) + 阅读进度 + 代码复制 + Mermaid 点击放大灯箱；去噪降密（无巨型篇号/光晕/重颗粒）。这些 `reader/` 套件已内置。

## 配套工件

- 上游官网截图（核验主题用）可存 `assets/<slug>-site-*.png` 留作参考。
- 卷内 `README.md`：本卷目录表（part 编号 + 文件 + 主题）。

## 验证（Definition of Done）

1. **每篇都标注 `文件:行号`**，可作代码导航索引。
2. **part-00 含概念入门释疑层**，生僻术语有解释。
3. **交叉引用是可点击的 markdown 链接**（本地起 `python3 -m http.server` 后点击可跳转）。
4. **Mermaid 图能渲染**；浅/深主题下文字都清晰（灯箱里的图带 `var(--ink-3)` 底卡）。
5. **主题经官网实测核验**，非臆测。
6. 推送后 GitHub Pages 可读（`https://<user>.github.io/<repo>/source/<slug>/`）。

## Gotchas（踩过的坑）

- **上游配色必须实测**：JS 框架站点要等水合再读样式；视觉模型也可能误判（如把"极细衬线"读成"无衬线粗体"），以 CSS 实测为准。
- **浅色主题**会暴露硬编码深色：阅读器套件里书脊渐变端、顶栏背景、晕影、代码文字色都要主题化（用 `--ink-deep` / `--code-fg` 变量），不能写死 `#100d08` / `rgba(20,16,10,…)`。代码块恒为深色岛、文字固定浅色 `#f1e9d8`。
- **Mermaid 调色板**要读主题 CSS 变量（ink/ink-3/bone/accent-deep）并按画布明暗选 `default`/`dark` 主题；`.prose .mermaid` 背景用 `var(--ink-3)`。**灯箱里的克隆 SVG 必须带与页面同色的底卡**，否则浅色主题下深墨图落在深底灯箱里不可见。
- **"部" vs "篇"**：书的结构单位用"篇"。批量改名时带负向断言保护 `部分/部署/内部/外部/全部/头部`。
- **阅读体验**：居中窄带 + 重装饰（巨型篇号/光晕/颗粒）不适合长读；改文档站式（左锚定 + 右轨 + 去噪）。
- **GitHub Pages** 用根目录 `index.html`、相对路径（base 是 `/<repo>/`）；阅读器 `fetch` 需 http，本地预览要起服务器。
