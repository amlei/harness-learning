# study-notes

把任意来源的学习内容，整理成一本第三人称、按功能分章的"实现剖析"书。

## 它解决什么问题

用户和 AI Agent 聊天学完一堆东西后，散落在对话里的知识很难回看复用。本 skill 把这些内容**重写成书**：
不是流水账、不是问答记录、不是使用手册，而是反过来追问"这套东西是怎么被造出来的"——以第三人称撰写，
有目录（部/章/节），按**功能领域**分章。最终产出一组互相连贯、可独立阅读的 markdown 文件。

## 关键不变量（写之前先记住）

1. **来源无关**——本 skill 不关心内容从哪来。用户传什么就读什么：opencode 会话、聊天记录文件、文档、文章、
   一段粘贴的文本均可。永远不要假设来源是某个固定形式。处理不同来源的方法见 `references/sources.md`。
2. **"学习笔记"≠"使用手册"**——挖的是**实现方式与设计思想**，不是"怎么用"。写"它如何工作、为何这样设计"，
   不写"用户该怎么操作"。如果原文是问答，要提炼成陈述性剖析。
3. **第三人称**——全程第三人称，像写一本书。禁止"我学到了""我们讨论了"；用"该系统采用……""可以发现……"。
4. **按功能分章**——每个功能领域一个文件（如 tool、prompt、provider 各自一章）。绝不按时间顺序或对话顺序组织。
5. **Mermaid 管复杂，ASCII 管简单**——复杂的关系/架构/状态流转用 Mermaid；简单流程、对照表、小图用 ASCII。
   不要对简单内容用 Mermaid（过重），也不要对复杂关系用 ASCII（看不清）。

## 工作流程

### 1. 接收并读取来源

用户会指定来源（路径、URL、会话标识、粘贴文本等）。把它读全——这是质量的根。
**如果来源是问答/对话，必须读到完整的"讲解"部分**（不只是问题），否则无法提炼实现细节。

- 来源很大时，先抽取**实质讲解**（去掉寒暄、进程噪声、纯操作日志），分文件落盘到临时目录再逐个读。
- 一次读不完就分批，不要省略。

### 2. 识别功能领域（分章的依据）

通读后，按**功能/机制**归类主题。例如同一段对话里既聊了工具分发又聊了记忆机制，就要拆成"工具"和"记忆"两章。
判断标准：能否独立成章、有没有完整的实现机制可剖析。

- 把纯操作/排错/测试的对话剔除（它们不是"实现剖析"的素材）。
- 一个功能领域素材太多时，拆成多章（如"工具"拆成 dispatch / 可见性 / 扩展三章）。

### 3. 与用户确认书的结构

这是必经的一步——**先确认再动笔**。向用户提出：分几个部（Part）、每部几章（Chapter）、每章几节（Section），
章节如何命名。给出具体方案让用户确认或调整。

确认要点：
- 部/章/节三级层级；
- 每个功能领域映射到哪一章；
- 文件命名（建议 `NN-功能名.md`，NN 为章节序号）；
- 放在 `source/`（源码/实现学习）还是 `paper/`（文章/资料）——遵循仓库的 source/paper 约定。

### 4. 撰写各章（实现机制深挖）

每章聚焦实现机制与设计思想。结构参考下方模板。**用原文里的真实证据**（代码引用 `文件:行号`、数据结构、
配置示例）支撑论述；没有证据的地方不要编造。

- 写之前，把该章用到的 Mermaid / ASCII 图想清楚：哪几个是复杂关系（Mermaid），哪几个是简单对照（ASCII）。
- 每章末尾给一句收口的"小结"，并衔接下一章。

### 5. 维护目录索引

`source/README.md`（或对应目录的 README）是书的目录 + 前言：列出全部部/章/节，含链接，
说明阅读约定（代码引用格式、术语、图例）。每新增/调整章节都要同步更新它。

### 6. 自检（写完必做）

对照下方"质量校验"逐条检查，不通过就修。

## 输出格式模板

每章按这个结构写，按需增删节：

```markdown
# 第 N 章　<章名>

> 一句话点出本章主题与核心张力（1-2 句）。

---

## N.1 <节名>
<实现机制剖析：用真实证据（代码引用/数据结构/配置）支撑。>
<复杂关系用 Mermaid；简单流程/对照用 ASCII 或表格。>

## N.2 <节名>
...

---

## 小结
<2-4 句收口：这章揭示了什么、为何这样设计。衔接下一章。>
```

目录（`README.md`）按这个结构：

```markdown
# <书名>

> 前言：这本书是什么、怎么读、图例约定。

## 目录

### 第 X 部分　<部名>
<一句话说明这部分的主题。>

- [第 N 章　<章名>](./NN-slug.md)
  - N.1 <节名>
  - N.2 <节名>

### 第 Y 部分　<部名>
...
```

## 质量校验（写完逐条对）

- [ ] 全文第三人称，没有"我/我们"式第一人称叙述。
- [ ] 按功能分章，没有按对话时间顺序。
- [ ] 写的是实现机制与设计思想，不是使用说明。
- [ ] 复杂关系用了 Mermaid，简单内容用了 ASCII/表格，没有混用错位。
- [ ] 代码引用形如 `文件名:行号`，引用的是来源里真实存在的证据，未编造。
- [ ] 目录 README 已更新，章节链接、部/章/节层级完整。
- [ ] 放置位置符合仓库 source/paper 约定。

## Gotchas

- **"学习笔记"是挖实现，不是记问答**——最常见的错误是把问答原样改写成对话体。要提炼成第三人称的剖析陈述，
  把"用户问、AI 答"变成"系统这样实现、原因是……"。
- **Mermaid 不能滥用**——每个 Mermaid 图都要有真正的多节点关系值得画；两三个框的简单流程用 ASCII 更轻。
  反过来，dispatch 分叉、并发层级、状态机这种多分支关系必须用 Mermaid，ASCII 会糊成一团。
- **来源是问答时，"问题"只是线索，"讲解"才是素材**——只读到问题就动笔，必然写成空泛概述。
  务必读到完整的讲解/推理/证据再写。
- **分章粒度看素材体量**——一个功能领域素材少就合成一章；素材多（比如"工具"聊了一整天）就按子主题拆成多章，
  否则单章臃肿难读。
- **不要造证据**——来源没讲到的细节（行号、字段名、数据结构）宁可模糊带过，绝不可编造 `文件:行号`。
- **第三人称不是冷冰冰**——可以用"可以发现""这意味着"等引导读者，但主语永远是"系统/该机制"，不是"我"。
- **目录是活文档**——章节一变，README 必须同步；读者第一眼看到的是目录，过期的目录比没有更糟。
